## 2. Boundary và transaction contract

| Thành phần | Contract |
|---|---|
| PaymentCommandApi | topup/withdraw/transfer nhận actor server, key và immutable input; trả PaymentReceipt |
| PaymentFacade | `NEVER`: không chạy trong transaction caller; validate → resolve owned wallet kể cả FROZEN → hash → executor |
| PaymentExecutor | `REQUIRED`: INSERT PROCESSING → wallet/history → flush JPA → UPDATE COMPLETED/result → đọc snapshot đã lưu; proxy commit xong mới trả HTTP |
| Duplicate claim | Chỉ duplicate tại idempotency INSERT tạo ClaimConflict; rollback executor hoàn tất rồi facade gọi reader proxy với transaction mới |
| PaymentReplayReader | Read transaction mới; COMPLETED/cùng hash trả snapshot, khác hash 409; không gọi lại bank eligibility/posting |
| JdbcIdempotencyStore | `MANDATORY`, cùng datasource/JPA transaction manager; không tự commit/REQUIRES_NEW |
| Session timeout | Mọi connection app/test dùng UTC và SESSION innodb_lock_wait_timeout=2; không SET GLOBAL |

PROCESSING không commit độc lập. Mọi lỗi trước commit rollback key, balance/version, history và result. Request lỗi không cache; key chưa commit có thể dùng lại với payload khác. Claim timeout MySQL 1205 trả REQUEST_IN_PROGRESS, retryable=true, Retry-After: 1. Không suy ra hash mismatch khi row đang bị giữ lock.

## 3. Request và hash

- Key case-sensitive ASCII `[A-Za-z0-9._:-]{1,64}`, không trim. V2 unique `(actor_id,operation,idempotency_key)` với ascii_bin.
- Strict JSON tại cả topup/withdraw/transfer: từ chối duplicate/unknown fields, amount chuỗi/float/exponent/ngoài long, bank ID bị coercion, root không phải object, trailing JSON và description không phải string/null.
- Validation trước claim: amount dương, description tối đa 255 UTF-16 units theo policy v1; target không có whitespace đầu/cuối; dữ liệu Unicode phải hợp lệ để không xảy ra thay thế ký tự khi encode UTF-8.
- Missing/null description chuẩn hóa null; empty string khác null; không trim/casefold/Unicode-normalize description.
- Canonical UTF-8 compact JSON array giữ nguyên thứ tự đã chốt, số integer base10; SHA-256 lowercase. Không hash key hoặc raw body.
- Sáu fixture cross-parser tại `fixtures/idempotency-v1.json` phải khớp cả canonical text và hash, gồm Unicode/null/empty/max long.

Giới hạn HTTP body/amount-code bổ sung tại C04-A-r3: cap 16 KiB theo bytes trước parse, 413 PAYLOAD_TOO_LARGE; DTO @Min amount ≤0 trả INVALID_AMOUNT.

## 4. Response và HTTP errors

- Success giữ status 200, envelope timestamp/status/message/data và các TransactionResponse fields, kể cả explicit nulls. Không đưa key/hash vào response.
- V2 `response_body JSON` lưu toàn bộ success. Vì MySQL normalize key order/whitespace, **cả response đầu tiên và replay đều đọc representation đã lưu**; không render timestamp mới hoặc dựng lại theo state hiện tại.
- PaymentReceipt có status/version/body/reference/replayed nội bộ; REST trả raw stored JSON với Content-Type application/json. OpenAPI mô tả object success, không mô tả String transport là JSON string.
- Thời gian mới của payment/snapshot được ghi UTC; không rewrite dữ liệu cũ hoặc đổi precision của V1.

| HTTP | code | Contract |
|---|---|---|
| 413 | PAYLOAD_TOO_LARGE | Body trên 16,384 bytes; không claim/ghi tiền |
| 400 | IDEMPOTENCY_KEY_REQUIRED / IDEMPOTENCY_KEY_INVALID | Không claim/ghi tiền |
| 400 | INVALID_REQUEST / INVALID_AMOUNT | JSON/validation fail trước business writes |
| 400/404 | WALLET_NOT_ACTIVE, BANK_NOT_ACTIVE, INSUFFICIENT_BALANCE, SAME_WALLET, WALLET_NOT_FOUND, BANK_NOT_FOUND | Lỗi mới không cache key |
| 409 | IDEMPOTENCY_KEY_REUSED | Row COMPLETED cùng actor/op/key, khác hash; retryable=false |
| 409 | REQUEST_IN_PROGRESS | Claim lock timeout; retryable=true, Retry-After: 1 |
| 409 | CONCURRENT_UPDATE | Giữ optimistic protection hiện tại; retry facade hoàn chỉnh thuộc C05 |
| 401 | UNAUTHENTICATED | Auth vẫn bắt buộc cả khi replay |
| 500 | INTERNAL_ERROR | Outcome có thể chưa rõ, client retry cùng key; retryable=true |

Error model giữ fields cũ, thêm code/retryable/traceId; security entrypoint cũng trả metadata này. Không nhận trace ID tùy ý từ client. C09 vẫn sở hữu hardening/redaction tổng thể; C04 không tuyên bố hoàn thành toàn bộ security gate.

## 5. Schema và migration

- V2 thêm `idempotency_requests`: actor/op/key/hash, PROCESSING/COMPLETED, transaction/reference, response version/status/body JSON, created/completed DATETIME(6).
- FK scalar tới users/transactions, unique actor/op/key và transaction; không cascade delete. CHECK buộc COMPLETED có result đầy đủ và snapshot JSON object.
- DB rỗng apply V1+V2. DB Phase 1 được verify/baseline V1 rồi apply V2; business data không đổi. Migrations đã apply là immutable.
- C02 historical baseline tests vẫn target V1 để xác minh đúng bốn bảng; test C04 riêng kiểm tra fresh latest và upgrade V1→V2, restart không apply lại.
